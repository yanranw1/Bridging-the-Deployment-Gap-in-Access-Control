Please help me check this JSON dataset based on the following three rules only. Do not check other rules unless I explicitly ask.

The dataset has two important sections: ACP and CODE.

ACP usually looks like this:

ACP action means the permission/action name.
ACP resource means the arguments for that action, but written as one string.

CODE usually looks like this:

CODE api means the actual API/tool name.
CODE args means the arguments for that API, written as a JSON object.

The three things you need to check are:

Rule 1. Required vs optional arguments must follow the dispatch contract.

Each action/API has fixed required arguments and optional arguments. Required arguments must be present. Optional arguments can be included only when they are actually used. Do not use unsupported argument names.

Use this full dispatch contract:
search_emails
  required: query
  optional: max_results
  output:   {"emails": [{"id": (str)}]}

list_emails
  required: (none)
  optional: label, max_results
  output:   {"emails": [{"id": (str)}]}

get_email
  required: email_id
  optional: (none)
  output:   {"email": {"id": (str), "threadId": (str)}}

analyze_email
  required: email_id
  optional: aspects
  output:   {"analysis": {"email_id": (str), "aspects": (list), "threadId": (str)}}

send_email  (destructive)
  required: to, subject, body
  optional: cc, bcc
  output:   {"message": {"id": (str), "threadId": (str)}}

draft_email
  required: to, subject, body
  optional: cc
  output:   {"draft": {"id": (str)}}

draft_reply
  required: email_id, body
  optional: (none)
  output:   {"draft": {"id": (str)}}

send_draft  (destructive)
  required: draft_id
  optional: (none)
  output:   {"message": {"id": (str), "threadId": (str)}}

forward_email  (destructive)
  required: email_id, to
  optional: message
  output:   {"message": {"id": (str), "threadId": (str)}}

star_email
  required: email_id
  optional: (none)
  output:   {"message": {"id": (str)}}

delete_email  (destructive)
  required: email_id
  optional: (none)
  output:   {"message": {"id": (str), "trashed": (bool)}}

create_task
  required: title
  optional: due, notes
  output:   {"task": {"id": (str)}}

complete_task
  required: task_id
  optional: (none)
  output:   {"task": {"id": (str)}}

list_tasks
  required: (none)
  optional: max_results
  output:   {"tasks": [{"id": (str)}]}


Correct example for forward_email:

email_id: msg_123, to: [team@company.com](mailto:team@company.com), message: Please review this.

CODE api should be forward_email.

Wrong example:

Rule 2. ACP resource must use the exact string format "key: value, key2: value2".

ACP resource must always be a string. It should not be a JSON object.

Correct ACP resource format:

"resource": "email_id: msg_123"

or:

"resource": "email_id: msg_123, to: [team@company.com](mailto:team@company.com)"

or:

"resource": "title: Finish report, description: Submit final version by Friday"

Every argument must be written as key colon space value.

The format should be:

key: value

If there is more than one argument, separate them with comma and space:

key: value, key2: value2, key3: value3

The separator must be comma plus space. That means ", " is correct. Just "," is not correct.

Correct:

"resource": "email_id: msg_123, to: [team@company.com](mailto:team@company.com)"

Wrong:

"resource": "email_id: msg_123,to: [team@company.com](mailto:team@company.com)"

This is wrong because it is missing the space after the comma.

Wrong:

"resource": "msg_123"

This is wrong because it does not say what argument the value belongs to. It should be:

"resource": "email_id: msg_123"

Wrong:

"resource": {
"email_id": "msg_123",
"to": "[team@company.com](mailto:team@company.com)"
}

This is wrong because ACP resource must be a string, not a JSON object.

Wrong:

"resource": "Finish report, Submit by Friday"

This is wrong because each value needs a key. It should be:

"resource": "title: Finish report, description: Submit by Friday"

Optional arguments should only be included when they are actually used.

For example, forward_email has required email_id and to, and optional message.

If there is no message, use:

"resource": "email_id: msg_123, to: [team@company.com](mailto:team@company.com)"

Do not write:

"resource": "email_id: msg_123, to: [team@company.com](mailto:team@company.com), message: null"

Same for CODE args. If an optional value is not used, it is better to omit it.

Correct:

"args": {
"email_id": "msg_123",
"to": "[team@company.com](mailto:team@company.com)"
}

Avoid unnecessary null optional values like:

"args": {
"email_id": "msg_123",
"to": "[team@company.com](mailto:team@company.com)",
"message": null
}

Rule 3. ACP and CODE must match each other exactly.

For each ACP entry, find the CODE entry with the same id. Then check the following things.

First, ACP action must match CODE api.

Correct:

ACP:
{
"acp_id": 0,
"action": "forward_email"
}

CODE:
{
"code_id": 0,
"api": "forward_email"
}

Wrong:

ACP:
{
"acp_id": 0,
"action": "trash_email"
}

CODE:
{
"acp_id": 0,
"api": "delete_email"
}

This is wrong because ACP action and CODE api do not match. Also, trash_email is not a supported dispatch API. Use delete_email.

Second, ACP resource keys must match CODE args keys.

Correct:

This is correct because ACP has title and notes, and CODE also has title and notes.

Wrong:

ACP:

"acp_id": 0,
"action": "create_task",
"resource": "title: Finish report, notes: Submit final version by Friday"
}

CODE:
{
"acp_id": 0,
"api": "create_task",
"args": {
"title": "Finish report"
}

This is wrong because ACP resource has title and notes, but CODE args only has title. They must match.

Wrong:

"resource": "email_id: msg_123, to: [team@company.com](mailto:team@company.com)"

CODE:

"email_id": "msg_123",

This is wrong because CODE args has message, but ACP resource does not. If CODE uses message, ACP resource must also include message.

Correct version:

CODE:

Deny examples still need to follow these rules.

Even if decision is deny, the API/action names and argument names should still be valid.

For example, if the user says:

Forward it to the team.

This should be denied because "the team" is not a concrete recipient.

A reasonable deny example is:

ACP:
{
"acp_id": 0,
"decision": "deny",
"subject": "email_agent",
"action": "forward_email",
"resource": "email_id: msg_123",
"purpose": "forward the email to the team",
"condition": "the recipient is underspecified because 'the team' does not identify a concrete email address or group"
}

CODE:
{
"acp_id": 0,
"api": "forward_email",
"args": {
"email_id": "msg_123"
},
"decision": "deny",
"reason": "Forwarding requires a concrete recipient. The agent cannot infer which address or group 'the team' means."
}

This will be reported as missing the required to argument, and that is okay because the deny reason explains exactly why the required argument is missing.

Do not use wrong placeholder names like message_id, note, content, recipient, or trash_email just because the example is deny. Deny examples should still use the correct API names and correct argument names.
